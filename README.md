# Constrained learning for parameter estimation

**Does the training objective matter more than the architecture? A study in neural calibration of the Heston model.**

## Introduction

Calibrating the Heston model, that is, recovering its parameters from an observed volatility surface, is classically a slow optimization. It is repeated for every surface and is not guaranteed a unique answer. A neural network can learn the inverse map directly. Real surfaces carry no parameter labels, though, so the network is normally trained on surfaces generated by the model itself, and it ends up learning to invert Heston rather than to explain the market. The pricer is differentiable, so predicted parameters can be priced back into a surface and compared with the observed one. That adds an unlabelled market-data term to the training objective.

This project measures whether, at a fixed model size, putting that domain knowledge into the objective buys more than choosing a better architecture, and whether it changes which architecture wins. The experiment fully crosses three architecture families with two objectives (with and without the market-data term). Model size is equal across architectures and every configuration runs over several seeds. Testing uses market surfaces from a period later than any seen in training, and every configuration is compared with a classical optimizer on accuracy and speed.

## How to work

### Making progress

1. **Pick** the next ⬜ task whose inputs are already on `main`.
2. **Branch** from the latest `main` (see [Branch names](#branch-names)) and open a draft pull request.
3. **Work.** Commit freely and push at least daily.
4. **Record** every research or thesis decision as a [decision record](#recording-decisions) on the same branch. If the decision changes the plan, edit the tables above in the same pull request.
5. **Tick** the task above. Then mark the pull request ready, wait for CI, and squash and merge.
6. **Close the phase** when its last task lands, with a [checkpoint](#checkpoints).

```bash
git switch main && git pull                  # start from the latest main
git switch -c feat/6.1-heston-pricer         # one branch per task
# ...work and commit freely...
git push -u origin HEAD                      # push early
gh pr create --draft --fill                  # open a draft PR straight away
git fetch origin && git rebase origin/main   # stay current by rebasing
git push --force-with-lease
# when ready: tick the task, wait for green CI, then squash and merge
```

### Branch names

`<type>/<id>-<slug>`

- **type** is the kind of change (see the table below). The same word starts the commit message.
- **id** is the task ID from the plan (`6.1`), or just the phase number for a checkpoint (`2`). Leave it out for work outside the plan.
- **slug** is two to five lowercase words joined by hyphens.

| Type | For |
|---|---|
| `feat` | New code capability |
| `fix` | Bug fix |
| `test` | Tests only |
| `refactor` | Code restructuring with no change in behaviour |
| `exp` | Experiment configurations, runs and their analysis |
| `docs` | Notes, design documents, decision records, the protocol, this README |
| `thesis` | Thesis text, figures and bibliography |
| `chore` | Tooling, dependencies, CI, the publishing script, repository housekeeping |

```
docs/1.2-heston-market-mismatch
test/5.3-round-trip-recovery
feat/6.1-heston-pricer
exp/7.4-smoothing-ablation
thesis/4.5-chapter-2-draft
docs/2-checkpoint
fix/pricer-short-maturity-nan
```

### Pull requests and commit messages

- **One task, one pull request.** A large task can span several PRs that share its ID, and the last one ticks the task.
- **The PR title becomes the commit on `main`**, so it follows [Conventional Commits](https://www.conventionalcommits.org/). The format is `<type>(<scope>): <summary>`. The scope is the task ID, or the affected area for work outside the plan. The summary is imperative and lowercase with no full stop, and the whole title stays within 72 characters.
  ```
  feat(6.1): implement Heston pricer with analytic derivatives
  docs(2): close phase 2, protocol frozen
  fix(pricer): guard against NaN at short maturities
  ```
- **The PR description** says what changed, why, and how it was checked, and it links any decision records.
- Commits inside a branch are free-form, because they are squashed on merge.
- **No more than two PRs are open at once.** A third usually means one of them should be finished or split.

### Keeping a branch current

- **Rebase onto `main` and never merge `main` into a branch:** run `git fetch origin && git rebase origin/main`, then `git push --force-with-lease`.
- **Force-push only your own task branch, and always with `--force-with-lease`.** `main` is never rewritten.
- **Avoid stacking branches.** If task B needs task A, merge A first. If stacking cannot be avoided, wait until A is squash-merged and then move B across with `git rebase --onto origin/main A B`, where `A` is the local, pre-squash branch.

### Merging

- **Merges use squash and merge only.** One task becomes one commit on `main`, titled by its PR.
- A PR is merged only when the branch is up to date with `main`, CI is green, the diff has been self-reviewed on GitHub, and the task is ticked.
- The branch is deleted on merge.

### Recording decisions

The [decision log](docs/decisions/) is where the reasoning behind the research and the thesis lives, so that nobody, including future you, has to reconstruct why something is the way it is. Records also become the justifications in Chapters 2 and 3.

**Write a record when:**

- you make a research choice an examiner could question ("why this and not that?"), for example about the architectures, metrics, baseline, data, objective or analysis;
- you make a thesis choice that shapes the argument, for example its scope, the structure of a chapter, or what counts as the contribution;
- you change the research plan: add, drop, split, move or materially reword a task, or change a checkpoint;
- you amend the protocol after `phase-2`.

**Don't write a record for:**

- **Workflow, tooling and infrastructure.** Those rules simply live in this README.
- **Routine implementation choices.** They belong in a code comment or the PR description.

**How to write one:**

1. Copy [`docs/decisions/template.md`](docs/decisions/template.md) to `docs/decisions/NNNN-short-title.md`, using the next free number.
2. Fill it in and add it to the [index](docs/decisions/README.md).
3. Commit it on the branch of the task it belongs to. A decision outside any task gets its own `docs/` branch.

**Status:** a record is *Proposed* while the question is open and *Accepted* once decided. An accepted record is never rewritten. To change your mind, write a new record and mark the old one *Superseded by NNNN*.

[`docs/thesis-plan.md`](docs/thesis-plan.md) is never edited. The current plan is these tables plus the decision log.

### Checkpoints

1. When the last task of a phase is merged, open `docs/N-checkpoint` with the title `docs(N): close phase N`. It marks the phase ✅ and adds a short note under the phase covering what was delivered and which decision records were accepted during the phase.
2. Once that PR merges, tag its commit and push the tag:
   ```bash
   git tag -a phase-N -m "Phase N: <outcome>"
   git push origin phase-N
   ```
3. Publish the tag as a GitHub Release with the same note.

Tags (`phase-N` and `draft-N`) are never moved or deleted. Phases can overlap: a later phase may start whenever its own inputs are on `main`. Two orderings, however, are hard rules:

- **No reportable experiment runs before `phase-2` exists.** That tag is the pre-registration: metrics, baseline, split and seeds are fixed in writing before any result exists. Any later change needs a decision record that amends the protocol, and it is reported as a deviation in the threats to validity (7.6).
- **No component lands before its tests.** A Phase 6 component is merged only once its Phase 5 tests are on `main`.

### Reportable results

- Every number in the thesis comes from a run launched on a commit on `main` with a clean working tree. The run record stores the commit SHA, the configuration and the seed. Runs from task branches are exploratory only, because squash merging discards their commits.
- If a fix touches code that produced reported results, those runs are repeated and the next checkpoint note says so.

### Drafts and supervisor review

The repository is where the thesis is written. Overleaf is where the supervisor reads it, comments on it and suggests edits. Content moves between the two only when you decide, in a cycle:

```
publish draft N → supervisor reviews → you triage in Overleaf → collect into a PR → keep writing → publish draft N+1
```

Both scripts are written in task 0.6.

**1. Publish a draft.** Do this when a chapter or a round of edits is worth showing. Merging to `main` never updates Overleaf by itself.

- Merge the thesis work you want to show into `main` as usual.
- Run `scripts/publish-draft`. It:
  - takes `thesis/` exactly as it is on `origin/main`, whatever you have checked out;
  - pushes it to Overleaf as one commit titled `Draft N (<sha>)`;
  - tags that commit on `main` as `draft-N`.
- Tell the supervisor that draft N is up, and what changed since the last one.

**2. The supervisor reviews in Overleaf.** They leave comments and suggest edits. Track changes is on for everyone in the project, so even a direct edit arrives as a suggestion you can accept or reject.

**3. You triage in Overleaf.**

- **Suggested edits:** accept or reject each one. Accepted edits become part of the Overleaf text.
- **Comments:** copy each one into `docs/reviews/draft-N.md` (from the [template](docs/reviews/template.md)), noting what you'll do about it. Then reply to it and resolve it in Overleaf. Comments exist only in Overleaf, and a later publish can delete them, so this file is their lasting record.

**4. Collect the accepted edits.** Run `scripts/collect-review`. It:

- fetches the Overleaf project;
- takes everything that changed there since `draft-N`;
- applies it to `thesis/` on a new branch `thesis/review-draft-N`, on top of anything you've written since.

Review the diff in your editor, add `docs/reviews/draft-N.md` to the same branch, open a pull request and squash-merge it as usual.

**5. Keep writing, then publish the next draft.** Comments that need real work go into the relevant `thesis` task, or into 8.5. Feedback that changes the plan becomes a [decision record](#recording-decisions).

**Rules:**

- **Write only in the repository.** In Overleaf you only accept or reject suggestions and answer comments.
- **Never publish into an open review.** A push from git can delete or misplace open comments and tracked changes in Overleaf. `publish-draft` therefore refuses while Overleaf holds edits that haven't been collected, and it asks you to confirm that every comment and suggestion is resolved.
- **Overleaf's Git access has limits.** It needs an Overleaf premium licence (AGH provides one) and a personal Git token. Its remote has one branch and does not accept force pushes. Both scripts therefore build on top of Overleaf's history and never rewrite it.
- **The fallback is a PDF.** If Git access stops working, publishing means tagging `draft-N` and sending the PDF built from that tag. Feedback then arrives by email and still goes into `docs/reviews/draft-N.md`.

**Overleaf project settings:**

- Invite the supervisor by email with a role that lets them comment and suggest edits. Overleaf calls it Reviewer; if that role isn't offered, Editor works too.
- Turn on track changes for everyone.
- A view-only link lets people read but not comment, so it is only for other readers.

**What the draft tags give you:**

- **A record of what the supervisor read.** Every version they saw is a tag, and its review notes sit in `docs/reviews/`.
- **What changed between drafts.** `git diff draft-2 draft-3 -- thesis/` shows the changes, and `latexdiff` can turn the same two tags into a marked-up PDF for the supervisor.
